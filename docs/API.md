# API reference

REST API served by `gaia-backend`. On the network it is only reachable over
HTTPS through the bundled proxy, `https://<server>:8443`; plain HTTP on port
8000 is bound to the server's loopback. The QGIS plugin is the primary
consumer; the API is stable enough to integrate against directly.

Interactive documentation is generated by FastAPI at `/docs` (Swagger UI) and
`/redoc`. Both require authentication.

## Authentication

Every request must carry a shared secret in the `X-API-Key` header, matching
`GAIA_API_KEY` in the server environment.

```bash
curl -H "X-API-Key: $GAIA_API_KEY" https://<server>:8443/projects   # from the network
curl -H "X-API-Key: $GAIA_API_KEY" http://localhost:8000/projects    # on the server itself
```

| Response | Meaning |
|---|---|
| `401 {"detail": "Missing X-API-Key"}` | No header sent |
| `401 {"detail": "Invalid X-API-Key"}` | Header does not match the server key |

`GET /status/ping` is the **only** unauthenticated endpoint. It returns no data
and exists so container healthchecks and the plugin's "is this URL reachable"
test work before a key has been configured.

There are no user accounts or roles — one key grants full access. See
[SECURITY.md](../SECURITY.md).

## Endpoints

### Projects

A project is a named container for runs.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/projects` | List all projects |
| `GET` | `/projects/{project_id}` | Single project |
| `PUT` | `/projects` | Create a project (body: `ProjectBase`) |
| `DELETE` | `/projects/{project_id}` | Soft-delete (sets `is_active = false`) |

`PUT` is used for creation rather than `POST` — unconventional, but it is what
the client sends.

```jsonc
// ProjectBase — request body for PUT /projects
{
  "name": "Malmö centrum",          // required
  "description": "Test area",       // optional
  "created_by": "user@example.se",  // required
  "attributes": {}                  // required, free-form object
}
```

Responses use `ProjectPublicSimple`, which adds `id`, `created_at`,
`updated_at` and `is_active`.

### Runs

A run is one execution of the pipeline over a bounding box.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/runs?project_id=<id>` | List runs for a project (`project_id` required) |
| `GET` | `/runs/{run_id}` | Single run |
| `POST` | `/runs` | Create and queue a run (body: `ProjectRunInsert`) |
| `DELETE` | `/runs/{run_id}` | Delete a run |
| `GET` | `/runs/{run_id}/status` | Progress (`ProjectRunStatus`) |
| `GET` | `/runs/{run_id}/download` | Download results as a ZIP |

```jsonc
// ProjectRunInsert — request body for POST /runs
{
  "name": "Kvarteret Ekorren",
  "run_type": "RunItAll",
  "project_id": 12,
  "attributes": {
    "bbox": "374000,6165000,374500,6164500",  // min_x,max_y,max_x,min_y
    "confidence_level": 75,                   // 0 < n <= 100
    "interface_to_use": [3, 4]                // interface ids from /models/segmentation
  }
}
```

`run_type` is one of `SegmentArea`, `CompareToBaseImage`, `Vectorize`,
`RunItAll`.

> **`bbox` ordering.** It is `min_x, max_y, max_x, min_y` — *not* the
> conventional `min_x, min_y, max_x, max_y`. See
> [ARCHITECTURE.md](ARCHITECTURE.md#imagery-and-tiling-parameters).

`attributes` is validated server-side: a missing `confidence_level`, an empty
`interface_to_use`, or a `bbox` without exactly four components is rejected.

```jsonc
// ProjectRunStatus — GET /runs/{run_id}/status
{
  "status": 2,                    // TaskStatusEnum
  "message": "Segmentering pågår",
  "calculating": false,           // true while total_steps is still unknown
  "finished_tasks": 2,
  "total_tasks": 6,
  "current_task_name": "SegmentProcess",
  "total_finished_step": 7,
  "total_steps": 17
}
```

`total_steps` is not known when a run starts — it depends on how many tiles the
bounding box produces. `calculating: true` means progress is not yet meaningful.

### Models

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/models/segmentation` | Selectable object types |

Returns every **active and installed** interface in the `Classification` group:

```json
[{ "id": 3, "name": "Segmentation - Buildings (ResUNet)", "description": "..." }]
```

The `id` values are what go into `interface_to_use`.

> An interface whose environment failed to install is set inactive and silently
> disappears from this list — which empties the object-type selector in QGIS.
> If this returns `[]`, see [OPERATIONS.md](OPERATIONS.md).

### Engine callback

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/run_result/{step_external_id}` | Engine reports step completion |

Called by engine subprocesses, not by clients. The `callback_url` passed to each
interface points here.

```jsonc
{ "task_step_id": 42, "success": true, "error": null, "additional_info": null }
```

### Status

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `GET` | `/status/ping` | **no** | Liveness |
| `GET` | `/status/verify` | yes | Full health check (`SystemStatus`) |
| `GET` | `/status/interfaces` | yes | Installed interfaces; `404` if none |
| `GET` | `/status/db-pool-status` | yes | Connection pool metrics |

`/status/verify` is the best single diagnostic — each component reports
`{ok, message}`:

```json
{
  "database":              {"ok": true,  "message": "..."},
  "migrations":            {"ok": true,  "message": "..."},
  "engine_filesystem":     {"ok": true,  "message": "..."},
  "storage_filesystem":    {"ok": true,  "message": "..."},
  "active_interfaces":     {"ok": false, "message": "..."},
  "installing_interfaces": {"ok": true,  "message": "..."},
  "poller":                {"ok": true,  "message": "..."}
}
```

## Status codes and enums

| Code | Meaning |
|---|---|
| `200` | Success |
| `401` | Missing or invalid `X-API-Key` |
| `404` | Not found (also: no interfaces installed) |
| `422` | Validation error — malformed body or path parameter |
| `500` | `"Something went wrong"` — details are in the server log only |

`500` responses are deliberately opaque. The traceback goes to the container
log via `exception_handling_middleware`; nothing is returned to the caller.

**`TaskStatusEnum`** — used for both tasks and runs:

| Value | Name | Meaning |
|---|---|---|
| `0` | `PENDING` | Created, not yet queued |
| `1` | `QUEUED` | Waiting for the dispatcher |
| `2` | `RUNNING` | Executing |
| `3` | `FINISHED` | Completed successfully |
| `4` | `ERROR` | Failed |
| `5` | `KILLED` | Cancelled, or failed because another task in the run failed |

A single failure marks every remaining task in the run `KILLED` — so `KILLED`
usually means "something else broke", not "the operator cancelled this".

## Notes for integrators

- **No pagination.** `GET /projects` and `GET /runs` return everything.
- **No rate limiting.** A client can queue unlimited runs.
- **Runs execute strictly one step at a time**, globally — not per run. A long
  run blocks every other run on the server.
- **Deletes are soft** for projects (`is_active = false`); result files on disk
  are not removed.
